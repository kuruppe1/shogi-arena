# RESEARCH.md — バズ投稿リサーチ手法

x-engineのネタ・型を作る前提となる、Xでの実投稿リサーチの手順書。
topics.md / templates.md を更新するときはこの手法に従う。

## 目的

「なぜその投稿がバズったのか」を、単一事例の目視ではなく、
複数ジャンル・複数アカウントを横断した基準で判定できるようにする。

## 「バズった」の判定基準

### ステップ1: 足切り(ノイズ除去)
以下を満たさない投稿は母集団に入れない。
- リプライ投稿は除外(`-is:reply`)
- RT+引用RT合計が10未満の投稿は除外(拡散していないものは正規化計算のノイズになるだけ)

### ステップ2: フォロワー数で正規化したスコア
```
スコア = (RT×3 + 引用RT×3 + リプライ×2 + いいね) ÷ max(フォロワー数, 10)
```
分母の下限を10にして、フォロワー1〜2人のアカウントで割り算が暴発するのを防ぐ。
フォロワー数そのもので対象を除外はしない(小規模アカウントのブレイクも拾うため)。

### ステップ3: 「バズった」のライン
絶対値を先に決め打ちせず、集めたデータの分布内で相対的に決めるのが原則。
参考として運用で使っている具体ライン:
- **アカウントのフォロワー数: 3,000〜1万人**(今のアカウントが現実的に目指せる規模帯)
- **投稿のインプレッション: 30万〜100万**(フォロワー規模に対して大きく跳ねた域)
- 目安の副指標: いいね500〜2,000、またはRT100〜500以上
- 足切り通過分の中でスコア上位10%、またはRT+引用RT合計500以上を「真のブレイク」として別枠記録

## リサーチの2チャンネル

### A. 無料: Xの高度な検索(x.com/search-advanced)
- クエリ演算子で `min_faves:` `min_retweets:` が直接使える(Web UIのみ。有料APIの現行プランでは同演算子は権限エラーになり使えない)
- キーワードは**フレーズ完全一致(引用符で囲む)**にしないと無関係な語にマッチする(例:「便利グッズ」が「便利屋68」に誤マッチした事例あり)
- ソートは「話題」(関連度・全期間から)を使う。「最新」は直近投稿に偏りノイズが増える
- 弱点: 1件確認するのに画面遷移・スクロールが要り、手作業なので大量件数には向かない

### B. 有料: X API (従量課金 $0.005/read)
- `sort_order=relevancy` を使うと新着順より反応の良い投稿が拾いやすい
- 検索エンドポイントに `min_faves` 等のフィルタ演算子は使えない(プラン制限)ため、**取得後にクライアント側でステップ1・2のスコアを計算してフィルタする**しかない
- ランダムなキーワード検索でこの基準に到達する的中率は実測で**約0.3%**(677件中2件)。大量にキーワード検索するのは費用対効果が悪い
- 効率が良いのは、**Aの手法や過去の当たりですでに見つかった好成績アカウントのタイムラインを直接取得する**方法(そのアカウントが型を再現しているかの検証にもなり、ヒット率が高い)
- Recent Search APIは直近7日間しか遡れない(全期間はEnterprise級の別料金)

## 実務上の運用

1. まずAの無料検索で、ジャンルごとに候補アカウント・投稿を探す
2. 見つかった当たりアカウントは、Bの API でタイムラインを取得し、型の再現性(他の投稿でも基準を満たすか)を確認する
3. 新しいジャンル・キーワードの探索はAで行い、Bはピンポイントの深掘り(タイムライン取得・大量サンプルでの分布確認)に使う。Bを無条件のキーワード検索に使わない(的中率が低すぎるため)
